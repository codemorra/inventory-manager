# Application backup format

Data backups use a versioned ZIP format distinct from the single-inventory exchange format. Version 1 contains `backup.json`, `inventory.db` and `attachments/<attachment-id>.blob` for each active managed attachment, including unclaimed uploads. SQLite retains all tables, identities, timestamps, revisions, templates, views, automatic-number counters and deletion tombstones. Deleted attachment bodies and unreferenced files are excluded; their retained database records remain subject to ordinary cleanup.

## Manifest

`backup.json` identifies `format: "inventory-manager-backup"`, `version: 1`, a UUID `id`, UTC `created_at`, `kind` (`manual`, `automatic` or `pre-restore`) and a `files` array. Each file entry declares its exact archive `path`, nonnegative safe-integer `byte_size` and lowercase hexadecimal SHA-256 digest. Paths must be unique; exactly one database is required. The manifest does not list itself. Manual creation and safety backups before restoration are available; automatic scheduling follows separately.

SQLite's backup API incorporates committed WAL content into the self-contained snapshot.

## Creation and validation

`POST /backups` creates a manual backup in the current configured backup directory and returns HTTP 201 with `id`, generated `filename`, `created_at`, `kind` and compressed `byte_size`. The response uses `Cache-Control: no-store` and exposes no filesystem path. No body is required. The runtime holds new requests, drains existing requests/streams and tracked asynchronous work, and suspends scheduled file cleanup until the operation finishes. Backups and live storage relocation share this exclusive runtime coordination. A client disconnect does not cancel an accepted durable backup operation.

Creation snapshots SQLite into private temporary storage and verifies managed originals against their database sizes and available SHA-256 hashes. A private directory beside the destination holds the ZIP, permitting the data, temporary and backup directories to reside on separate filesystems. The completed archive is read back: exact entries, supported unencrypted ZIP Store/Deflate layout, regular file types, actual sizes, CRCs, SHA-256 hashes, SQLite integrity/foreign keys and attachment metadata must all pass. Archive entry names never become extraction paths; only the database is extracted to a generated private filename for verification. Attachments are verified as streams without retaining their bodies in memory or extracting duplicate copies.

Only a successfully verified ZIP is atomically renamed to a generated timestamp/UUID filename in the backup directory. Failure preserves application data and existing backups and removes private workspaces. An interrupted process may leave private `backup-XXXXXX` directories in temporary storage or `.backup-XXXXXX` directories in backup storage; startup reconciles these while holding the application lifetime lock. Unrelated names and completed backups are preserved. Source attachments must be regular files; links and special files are rejected.

Metadata is bounded to 64 MiB and archives to 524,290 entries, matching the existing archive processing bounds. These bounds do not impose a per-attachment or total ZIP byte-size limit. Additional disk space is required for the SQLite snapshot, its verification copy and the compressed backup. New requests remain queued during backup creation and verification.

Validation failures return 422 `invalid_backup_archive`; an unavailable exclusive operation returns 409 `backup_conflict`. Unexpected storage failures return 500. Waiting requests resume after either success or failure.

## Listing and download

`GET /backups` lists regular files matching the application's timestamp/UUID backup naming convention in the active backup directory, ordered by filename from newest to oldest. Each entry contains `filename`, compressed `byte_size` and `metadata` with `id`, `created_at` and `kind`. Listing reads and validates bounded manifest metadata without decompressing the database or attachment bodies. An unreadable manifest produces `metadata: null` for that entry, preserving access to other backups. Private publication directories, symbolic links, directories and unrelated filenames are ignored. API responses expose archive basenames rather than local filesystem paths.

`GET /backups/{filename}/download` streams the selected regular archive as `application/zip`, with attachment disposition, exact `Content-Length`, `Cache-Control: no-store` and `X-Content-Type-Options: nosniff`. `HEAD` returns the download headers without transmitting the body. Downloads are repeatable and preserve the archive. Invalid names, missing files and symbolic links return 404 `backup_not_found`. Requests and download streams participate in the existing runtime activity tracking, so storage relocation waits for active downloads to finish.

Settings > Backups loads the list when expanded and offers manual creation, refresh, native browser downloads and a delete action beside each download icon. Deletion uses the shared confirmation dialog to identify the selected archive before it is removed. Backup operations temporarily disable competing settings operations and dialog dismissal while awaiting their result. A successful creation remains visible if a subsequent list refresh fails. An uncertain creation or deletion response requires refreshing the catalog before another attempt.

`DELETE /backups/{filename}` removes the selected regular archive and returns 204. It uses the same generated-basename validation as downloads and rejects symbolic links, directories and unrelated names. Missing selections return 404 `backup_not_found`. An archive with an opening or active download, or a pending deletion, returns 409 `backup_conflict`; downloads likewise reject a pending deletion. Reservations are released when download streams close or an operation fails. Deletion participates in runtime activity tracking so storage relocation waits for it to settle. Archives with unreadable metadata can also be explicitly deleted.

## Checked restoration

The restore icon opens a checked preview of a saved backup. **Restore from file** opens the system file picker directly and prepares a checked preview after a ZIP is selected. Preparation streams a private copy into temporary storage, validates the complete ZIP, checks SQLite integrity and foreign keys, and compares the database schema and migration history with the installed application. Active inventory values, templates, table views, revisions, lifecycle relationships, automatic-number counters and attachment ownership must be consistent. Incompatible database schemas are rejected before confirmation. The summary shows the source timestamp and inventory, item and attachment counts. Previews expire after 30 minutes; canceled or expired selections cannot be confirmed.

Confirmation retains the exact selection identity, rechecks the copied archive's SHA-256 digest and extracts a fresh verified database and attachment set. The runtime drains active requests, streams and asynchronous services and holds new requests. It then creates and verifies a `pre-restore` safety backup of the current data. Failure to create this safety backup stops activation. The incoming database and attachment files are copied and synced into owned staging directories beside their respective live targets; this supports separate filesystems and an independent `INVENTORY_DB_PATH`.

The runtime checkpoints and closes SQLite before retaining the original database and attachment directory under private names and publishing the incoming copies. A synced `.restore-journal.json` in the fixed configuration directory records the operation and target paths. The new database must reopen successfully before the journal records committed activation. Startup resolves this journal before opening the application database or processing storage relocation: pending activation restores retained originals, while committed activation keeps the new resources and retries cleanup. Recovery checks target paths, staging ownership and the incoming database digest and refuses to initialize missing or unrecognized storage. Ownership markers remain until their staging directories have been emptied, making interrupted cleanup retryable.

A durable `.restore-receipt.json` retains the latest successful confirmation; its committed journal also supplies the receipt while cleanup is pending. Repeating a completed confirmation returns its original result instead of replacing data again. Prepared single-inventory import/export sessions are invalidated after activation. The restore response identifies the original backup, completion time and safety backup filename. Temporary selections are reconciled by maintenance; abandoned process workspaces are removed after 24 hours.

`POST /backup-restores` accepts either JSON `{ "filename": "<listed archive>" }` or an `application/zip` binary upload and returns HTTP 201 with a checked preview. `GET /backup-restores/{id}` reads preview or completion status, `DELETE /backup-restores/{id}` discards an unused selection, and `POST /backup-restores/{id}/confirm` explicitly activates it. These responses use `Cache-Control: no-store`. Expired or unavailable identities return 404 `backup_restore_not_found`; conflicting operations return 409 `backup_conflict`; invalid archives return 422 `invalid_backup_archive`. Confirmed operations finish independently of client disconnection. After an uncertain response, read the original identity's status before issuing another confirmation.

The runtime sends `X-Inventory-Generation` on responses and exposes it through CORS. API clients should retain the first observed generation and send it on later requests. Writes carrying an older generation return 409 `application_data_changed`; writes already queued before a restore also retain their original generation. The frontend pins this identity, blocks responses from a changed generation and requires an application reload. The confirming UI similarly requires a reload after successful restoration, clearing cached data and editing sessions before further work.
